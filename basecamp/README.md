# Escapement in Logos Basecamp: `escapement_core_module` and `escapement_ui`

A first version of the Logos Core module (M2) and the Basecamp mini-app (M3), built for **Logos Basecamp
0.4.0-rc.2** and LEZ **v0.4.0-rc3**. Prototype, not audited. Results of the runs: [RESULTS.md](RESULTS.md).

| Package | What it is |
|---|---|
| `escapement_core_module` | A Logos Core module (`type: core`, Rust, C ABI generated by logos-module-builder 5f74cdb) over `escapement-sdk` and `escapement-core`: reads and checks with the SDK, builds with the SDK's builders, signs LEZ rc3 public transactions only on `approve`. |
| `escapement_ui` | A QML mini-app (`type: ui_qml`) for Basecamp: Recipient and Creator views over the module. |

## What works

- **Reads** (`schedules`): for the account, every schedule the module knows on this network, read live from the
  sequencer: total, **locked** (not vested yet), **claimable now**, claimed, **next unlock in UTC** and why nothing more
  is claimable (the SDK's `next_unlock`), the vesting terms; the creator's own schedules likewise.
- **Public claim** (`prepare_claim` → `approve`): the SDK's `prepare_public_claim` checks (the signer is the
  beneficiary, something is claimable, the amount is at most that), `builders::claim_public` builds it.
- **Create one schedule** (`prepare_create` → `approve`): native asset, linear or cliff + linear, cancelable or not;
  `validate_schedule_params` (the program's own checks) before anything is built; the new schedule's id is shown.
- **Cancel** (`prepare_cancel` → `approve`): only by the cancel authority, only while cancelable; vested and refunded
  amounts shown before and read back after.
- **Signing only after approval, by the caller that prepared it.** `prepare_*` checks, builds and summarises (rows,
  effects, maximum fee); nothing is signed. Only `approve(pending_id)` signs, once, exactly what was prepared, when it
  comes from the caller that prepared it and the module is still on the network the prompt showed; a pending
  transaction expires after five minutes and is refused, before anything is signed, if the account's nonce moved.
  `reject` drops it (also only for the caller that prepared it). After the block the module reads the schedule back
  and says whether the program applied it.
- **A signed transaction keeps its hash.** Once signed, the transaction is recorded in the module's memory before it
  is sent (until the module restarts). If the sequencer's answer does not arrive, its block cannot be read, or the
  schedule cannot be read back (a failed read is never taken for a revert), the reply says so (`state: unknown` or
  `sent`, `applied: null`) with the transaction's hash; if the sequencer answers with a refusal, the state is
  `refused_by_sequencer`. The view keeps such a transaction in its own banner, with the full hash, until **Check**
  (`tx_status`) finds it in a block or the person dismisses it, whatever later refreshes or errors show; new
  transactions are held meanwhile.
- **Two callers.** The module serves its view (`module:escapement_ui`, the name Logos Core gives the mini-app) and the
  host (`host`: logosctl, or anything else that can reach the Logos Core daemon, which approves **without any prompt**).
  Every other Logos module, and any caller Logos Core cannot name (`unknown`), can call `version` and nothing else.
  `status` does not hand out the pending transaction's id. `approve` says who approved (`approved_by`).
- **The key** stays in the module: from a key file the person names (a regular file of at most 4 KiB, opened without
  blocking and checked again as opened: 64 hex digits, or `escapement keygen`'s JSON; read into a buffer wiped after
  use) or made by the module (`key new`, written mode
  0600 to its data directory). Only the account id and public key leave it.
- **Amounts** are typed in display units and converted to base units by string arithmetic (`qml/js/amount.js`, tested
  by `tests/amount.test.mjs`); the module takes and returns base units as decimal strings, never floats. The native
  asset's units are fixed in the module (LEZ, 9 decimals; no caller can change them), every amount in a prompt is
  shown in both units ("0.25 LEZ (250000000 base units)"), and the view shows no prompt in other units than it
  converted the amount with.
- **Token schedules** are listed in their own base units, named by their token definition (the module has no token
  metadata), and are never claimed or cancelled here: the module refuses, the view disables the buttons.
- **Plain text**: the view renders every text as plain text, so nothing from the module or the sequencer is read as
  markup (no hidden text, no fetched images).
- **The sequencer's address**: `http://` only to the literal addresses 127.0.0.1 or [::1] (not `localhost`, which goes
  through the resolver); `https://` elsewhere; there is no default remote endpoint; an address with a
  user name or password, `%`-escapes, a backslash, a query or a fragment is refused.
- **Plain errors**: the SDK's messages (`SdkError`, the program's codes 1..=35 as `codes::refusal` words them), the
  sequencer unreachable, the wrong signer, read-only networks.
- **Packaged and signed**: `.lgx` for linux-amd64 with Nix (`scripts/build-lgx.sh`), signed with an Escapement **test**
  key (`scripts/sign-test.sh`, "Escapement test build (not a release)"), installed in a headless Logos Core with
  `signature_policy: require` (`scripts/install-test.sh`, which also checks that both packages unsigned, one with a bit
  flipped, one with its manifest edited and one signed by another key under the test signer's name are refused) and in
  the Basecamp 0.4.0-rc.2 AppImage.

## What does not work yet

- **Private claim from the GUI: not yet.** The private claim (one-time alias, real or dev-mode proof) works with the
  `escapement` CLI and the e2e suite; the module does not prove and the view only links to the CLI path.
- **macOS: not built.** linux-amd64 only.
- **Token schedules, batches, milestone signals, transfer of the beneficiary, fee withdrawal**: CLI only.
- **No discovery without an indexer.** The module lists schedules it created or was given by id (`track`, "Add a
  schedule by its id"); LEZ's sequencer has no "accounts of a program" query, and no indexer runs here.
- **Fees are estimated, not simulated.** Without LEZ's executor in the module the gas limit is fixed: create 400,000;
  claim 250,000 (200,000 plus the SDK's 25%); cancel 200,000; against 140,553 / 79,500 / 77,506 cycles measured by the
  e2e suite. The sequencer charges what is used.
- **Signing is the module's own**, not yet Logos's wallet or signer modules (LP-0021's SDK is not released); the
  approval prompt is the view's. The host (logosctl, or anything that can reach the Logos Core daemon) can prepare and
  approve with no prompt at all; another module or an `unknown` caller can do neither.
- **A refresh clears an amount being typed** in a position's claim field (the list is rebuilt from each read).
- **Test key only.** The packages are signed with a test key made on the build box, not a release key.
- **The view calls the module from QML** (`logos.callModuleAsync`), which Basecamp 0.4.0-rc.2 runs but logs as
  deprecated ("Move the call into a backend module ... removed in the next breaking release"): the next Basecamp
  release needs the view's calls moved into a backend module.

## Install

Logos Basecamp 0.4.0-rc.2 (`logos-basecamp-x86_64.AppImage`, SHA-256
`e59e14cddd211bed763c49e6a9bdfea462b91123b368386bdb8f700527b747a0`):

1. **Manage Packages** → **Install Local Package** → `escapement_core_module-0.1.0.lgx` → the prompt names
   "Escapement test build (not a release)": that name is **self-asserted** (Basecamp logs it "self-asserted, not
   verified"); what identifies the signer is its key, which Basecamp shows as `B77D 19F8 F4EB 514C`, the test key's
   `did:jwk:eyJjcnYiOiJFZDI1NTE5Iiwia3R5IjoiT0tQIiwieCI6Im5xcnpobGxiTDFHVlQtMzdyQlVyb0FFZFdlcG5BVGpybGstakVQeDVoVU0ifQ`
   (`results/build/escapement-test.did`). Check it, then **Install**. Again with `escapement_ui-0.1.0.lgx`.
2. Open **Escapement** from the sidebar. Basecamp loads `escapement_core_module` itself.
3. **Network**: the sequencer's RPC (`http://127.0.0.1:3040` for `e2e/sequencer.sh start`; `https://` for a remote
   one) and the program id; **Connect**. **Account**: a key file's path → **Use key file** (or **New key**, then fund it).
4. **Recipient**: your positions; **Claim (public)…** → check the prompt → **Approve and sign**.
   **Creator**: beneficiary, total, vesting (start `now`, end `+30d` or a UTC time) → **Review and sign…** → approve;
   your schedules, **Cancel…**.

Headless (logosctl): `scripts/install-test.sh SIGNED UNSIGNED WORK` (see its header), or by hand:

```sh
logosctl daemon start --detach
logosctl key add escapement-test --did "$(cat keys/escapement-test.did)" --display-name "Escapement test build (not a release)"
logosctl package install escapement_core_module-0.1.0.lgx -y && logosctl module load escapement_core_module
logosctl call escapement_core_module configure '{"rpc_url":"http://127.0.0.1:3040","program":"<program id>"}' --json
```

## Build

```sh
basecamp/scripts/build-lgx.sh OUT                    # Linux x86-64 with Nix: OUT/linux-amd64/*.lgx (unsigned), build.json
basecamp/scripts/sign-test.sh KEYDIR OUT/linux-amd64 SIGNED   # a test key (made in KEYDIR if none); never a release key
basecamp/scripts/install-test.sh SIGNED OUT/linux-amd64 WORK  # headless Logos Core; FLOW_RPC/FLOW_PROGRAM/FLOW_KEYS: the flow
# The module's calls natively (no Logos Core): stage the crates and the builder's Rust SDK source, then cargo
python3 -I basecamp/scripts/stage.py
nix build github:logos-co/logos-module-builder/5f74cdb3cecacde054c68d72fcc0d2cfe2195900#rust-sdk-src \
  -o basecamp/escapement_core_module/logos-rust-sdk-src
node basecamp/escapement_ui/tests/amount.test.mjs        # the view's amount and time helpers
QT_QPA_PLATFORM=offscreen qmltestrunner -input basecamp/escapement_ui/tests/qml   # the view (plain text, prompts, reject)
basecamp/scripts/tests/test-sign-test.sh WORK            # sign-test.sh against a stand-in lgx
basecamp/scripts/tests/test-keyscan.sh WORK              # keyscan.py on fake keys
cd basecamp/escapement_core_module/rust-lib && cargo +1.98.1 test --locked -p escapement-module-calls
cargo run --release -p escapement-module-calls --example call -- --script SESSION.txt   # lines: [@CALLER ]METHOD JSON
```

The Nix build compiles the module with Rust 1.98.0 (`metadata.json`, the builder's rust-overlay has no 1.98.1); the
native tests above use 1.98.1, the workspace's `rust-toolchain.toml`. `scripts/keyscan.py DIR --jwk K --keyfile K`
searches what leaves a machine for a private key in its usual forms; the build and the Basecamp session record its
output (`results/`). `build-lgx.sh` records in `build.json` the git trees of `basecamp/escapement_core_module`,
`basecamp/escapement_ui` and `basecamp/scripts` it built from (`git rev-parse <commit>:<path>` gives them for any
commit), and `stage.py` records the staged crates' own last commit, so neither depends on later commits.

`stage.py` copies `escapement-core` and `escapement-sdk` into `rust-lib/staged/` (the builder copies only `rust-lib/`)
with their workspace fields resolved; LEZ v0.4.0-rc3 and the `lez-authority` crates stay git dependencies, fetched by
the builder at the commits in `rust-lib/Cargo.lock`. The transaction encoding (`calls/src/lez.rs`) is checked against
LEZ rc3's pinned message layout and BIP-340's vectors, and was accepted and executed by a LEZ rc3 sequencer.

## Module methods

Each takes one JSON string and returns one: `{"ok": true, ...}` or `{"ok": false, "error": "..."}`. All but `version`
answer only the view (`module:escapement_ui`) and the host; `prepare_*` replies carry `decimals`, `unit` and `network`.

| Method | Request | Reply |
|---|---|---|
| `version` | — | module, version, staged commit and crates' SHA-256, methods, what is not done |
| `configure` | `rpc_url`, `program`, `read_only?` (a JSON boolean; `decimals`/`asset_label` other than the fixed units are refused) | head block, chain clock (UTC), whether the program is configured, fee bps, the units |
| `status` | — | network, account (never the key), balance, whether a transaction waits (kind, age; not its id) |
| `key` | `action`: `import` (`path`), `new`, `show`, `forget` | account, public key, where the key came from |
| `schedules` | `beneficiary?`, `creator?`, `ids?` | `positions` and `created`: total, vested, locked, claimable now, claimed, next unlock (ms, UTC), status, terms |
| `track` | `schedule` | the schedule's row (it must be one of the program's) |
| `prepare_claim` | `schedule`, `amount?` (base units), `to?` | `pending_id`, title, rows, effects, maximum fee; nothing signed |
| `prepare_create` | `beneficiary`, `total`, `kind` (`linear`/`cliff`), `start_ms`, `end_ms`, `cliff_ms?`, `cliff_amount?`, `cancelable?` (a JSON boolean) | likewise, with the new schedule's id |
| `prepare_cancel` | `schedule` | likewise, with vested and refunded amounts |
| `approve` | `pending_id` | `tx_hash`, `state` (`in_block`, `sent`, `unknown` or `refused_by_sequencer`, with a warning or note), block, outcome read back (`applied`: true, false, or null when unread), `approved_by` |
| `reject` | `pending_id?` | what was dropped (only for the caller that prepared it) |
| `tx_status` | `tx_hash` | block and outcome of a transaction `approve` sent (`applied: null` when the schedule cannot be read back) |
