# Escapement — Verification Evidence Ledger

Every result below was produced by running the code in this repository against pinned upstream LEZ `v0.4.0-rc3` dependencies (`logos-blockchain/logos-execution-zone` tag `v0.4.0-rc3`, `logos-blockchain/lez-programs` branch `refactor/lez-v0.4.x` rev `cad71fc67d75ec9f6a07fc908f687678de7f7ed6`, and `mmlado/lez-admin-authority` tag `v0.2.0`).

**Honest status labels:**
- **Real STARK proof (`RISC0_DEV_MODE=0`):** Full RISC Zero 3.0.5 proof generated by `r0vm 3.0.5` on CPU, checked to be an `InnerReceipt::Succinct` (never `Fake`), and verified by LEZ through `ValidatedStateDiff::from_privacy_preserving_transaction` before `V03State::apply_state_diff`.
- **Real-ELF dev mode (`RISC0_DEV_MODE=1`):** Runs the actual compiled RISC-V guest binaries (`ESCAPEMENT_ELF`, `TOKEN_ELF`, `CLOCK_ELF`) inside `r0vm 3.0.5` and enforces every LEZ `V03State` rule and cycle budget (`MAX_GAS_EXEC = 10,000,000`), skipping STARK seal generation.
- **In-process `V03State`:** LEZ's actual state-transition engine running in process (not a live public testnet; LEZ testnet 0.4 has not launched as of 2026-11-20).
- **Nothing in this repository is audited yet.**

### Proving Time Note (Row E-02)
In Row E-02, `ESCAPEMENT_ELF` (`59,878` public cycles) runs publicly, outside the proof; the proving time is LEZ's privacy circuit plus the private `token::IncreaseBalance`. The run used no private fee account (`fee: None`), one private witness, and no padding; a production wallet transaction adds a private fee witness and padding, to be measured on desktop hardware in M5. Two consequences:
1. `Response::timestamp_window(effective_ts..)` instead of `clock_actor()` is required so a multi-minute CPU proof never expires before inclusion.
2. `escapement_core_module` needs persistent background proving jobs, because the proof exceeds Logos Basecamp's 20-second view-to-core call timeout several times over.

## Review History

On 2026-11-20 four fresh-context AI review agents (security, tests/CI, fact-check, RFP grading) audited the prototype; this is not a third-party audit. Fixed as a result, each with a test above: the same-block cancel over-refund on shared batch escrows (E-10, D-10), single-account fee routing that would have blocked multi-token creation once fees were on (E-05), a panic on schedule calls aimed at the config PDA (E-11), unvalidated `ClaimExact` timestamps on milestone and cancelled schedules (E-11), escrow self-lock destinations (E-11), user-reachable panics now metered (E-11), an inexact `next_unlock_after` (E-01), real-proof checks that now inspect the receipt type and every privacy surface (E-02), tautological rollback checks replaced by on-chain rollbacks (E-03), and CI that now runs `cargo fmt --check` and `cargo clippy -D warnings`.

A second round the same day, four more fresh-context AI review agents (security, tests/CI, fact-check, RFP grading), found no exploitable path in the program. Its one claimed security issue, a third party pre-initializing an escrow or fee-vault PDA, is not reachable on `v0.4.0-rc3` (D-11). It did find test gaps, now closed: nine guards that no test would have caught if deleted (guest authority checks on `Cancel`, `MakeNonCancelable`, and `TransferBeneficiary`; zero-address guards; broker fee caps; `ClaimExact`'s overclaim and nothing-claimable paths; the cancelled branch of `next_unlock_after`) are now covered (E-12, E-01); the invariant suite's negative probes went from 1 firing to 20 across 5 refusal classes, each asserting state unchanged (E-07); three property tests were added, including a fee-ceiling reference that shares no code with the implementation (E-01); the raced private claim in E-03 is pinned to its exact refusal (LEZ's nonce check); seven documentation errors were corrected; and CI now pins `RUSTUP_HOME`/`CARGO_HOME` with a host-toolchain smoke test and offers a manual job that reproduces the real STARK proof.
